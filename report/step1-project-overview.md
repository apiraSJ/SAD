# ส่วนที่ 1: ภาพรวมโครงการ (Project Overview)

---

## 1.1 Project Description

### ชื่อโครงการ

**ระบบแจ้งซ่อมอาคารนอน นักเรียนนายเรืออากาศ**

### หลักการและเหตุผล

ปัจจุบันการแจ้งปัญหาหรือความชำรุดภายในอาคารนอนสามารถเกิดขึ้นได้จากหลายสาเหตุ เช่น อุปกรณ์ไฟฟ้าชำรุด ห้องน้ำมีปัญหา เครื่องซักผ้า เครื่องทำน้ำเย็น ประตู หน้าต่าง เฟอร์นิเจอร์ หรือส่วนประกอบต่าง ๆ ของอาคาร โดยการแจ้งปัญหาอาจเกิดขึ้นผ่านช่องทางที่ไม่เป็นระบบ เช่น การแจ้งด้วยเอกสาร การแจ้งด้วยวาจา หรือการแจ้งผ่าน LINE ส่งผลให้ข้อมูลการแจ้งซ่อมกระจัดกระจายและยากต่อการติดตาม

ปัญหาดังกล่าวทำให้ผู้แจ้งไม่สามารถตรวจสอบสถานะของงานซ่อมได้อย่างชัดเจน ผู้รับผิดชอบอาจได้รับข้อมูลไม่ครบถ้วนหรือเกิดการแจ้งปัญหาซ้ำ และหน่วยงานที่เกี่ยวข้องไม่สามารถรวบรวมประวัติการซ่อมและค่าใช้จ่ายเพื่อใช้ในการติดตามและวิเคราะห์ได้อย่างมีประสิทธิภาพ

โครงการนี้จึงเสนอการพัฒนา **ระบบแจ้งซ่อมอาคารนอน นักเรียนนายเรืออากาศ** เพื่อเป็นศูนย์กลางในการรับแจ้งปัญหา ติดตามสถานะการซ่อม มอบหมายงานให้ผู้รับผิดชอบ บันทึกผลการซ่อมและค่าใช้จ่าย รวมถึงจัดเก็บประวัติการแจ้งซ่อมอย่างเป็นระบบ

### วัตถุประสงค์ของโครงการ

1. เพื่อพัฒนาระบบสำหรับแจ้งปัญหาและความชำรุดภายในอาคารนอน
2. เพื่อให้ผู้แจ้งสามารถติดตามสถานะของงานซ่อมได้
3. เพื่อช่วยผู้ดูแลอาคารในการตรวจสอบและมอบหมายงานซ่อมให้ช่าง
4. เพื่อจัดเก็บข้อมูลประวัติการซ่อมและค่าใช้จ่ายอย่างเป็นระบบ
5. เพื่อช่วยให้หน่วยงานที่เกี่ยวข้องสามารถตรวจสอบข้อมูลและภาพรวมของงานซ่อมได้สะดวกขึ้น

### ขอบเขตของระบบ

ระบบครอบคลุมกระบวนการหลักตั้งแต่การแจ้งปัญหาไปจนถึงการปิดงาน ได้แก่

**แจ้งปัญหา → ตรวจสอบ/รับเรื่อง → มอบหมายช่าง → ดำเนินการซ่อม → บันทึกผลและค่าใช้จ่าย → ปิดงาน**

ข้อมูลหลักที่ระบบจัดเก็บประกอบด้วยข้อมูลผู้ใช้ ข้อมูลอาคาร ห้อง รายละเอียดปัญหา ประเภทปัญหา รูปภาพประกอบ สถานะงาน ผู้รับผิดชอบ ผลการซ่อม และค่าใช้จ่าย

### กลุ่มผู้ใช้งาน

- **นักเรียนนายเรืออากาศ/ผู้อยู่อาศัย** — แจ้งปัญหาและติดตามสถานะงานของตนเอง
- **ผู้ดูแลอาคาร** — ตรวจสอบ รับเรื่อง และมอบหมายงานซ่อม ตลอดจนจัดการข้อมูลผู้ใช้และสิทธิ์
- **ช่างซ่อม** — รับงาน ดำเนินการซ่อม และบันทึกผลการซ่อม
- **ผู้บังคับบัญชา/ฝ่ายที่เกี่ยวข้อง** — ตรวจสอบข้อมูลและภาพรวมของงานซ่อม

### ผลลัพธ์ที่คาดว่าจะได้รับ

ระบบจะช่วยให้กระบวนการแจ้งซ่อมมีความเป็นระบบมากขึ้น ลดปัญหาการตกหล่นของข้อมูล ทำให้สามารถติดตามสถานะงานซ่อมได้ และมีข้อมูลประวัติการซ่อมและค่าใช้จ่ายที่สามารถนำไปใช้ประกอบการบริหารจัดการอาคารนอนได้

## 1.2 Alternatives

ในการพัฒนาระบบแจ้งซ่อมอาคารนอน สามารถพิจารณาทางเลือกในการจัดหาระบบได้ 3 แนวทาง ได้แก่ การจ้างหน่วยงานภายนอกพัฒนา การจัดซื้อซอฟต์แวร์สำเร็จรูป และการพัฒนาระบบด้วยทีมงานภายใน

| ทางเลือก                      | ข้อดี                                                                                                                                | ข้อเสีย                                                                                                      |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------ |
| **1. Outsource**              | ได้ระบบจากผู้มีประสบการณ์ สามารถลดภาระการพัฒนาของทีม และอาจได้รับระบบที่มีความพร้อมใช้งาน                                            | มีค่าใช้จ่ายสูง ต้องพึ่งพาผู้พัฒนาภายนอก และการปรับระบบให้ตรงกับความต้องการเฉพาะของหน่วยงานอาจทำได้ยาก       |
| **2. ซื้อซอฟต์แวร์สำเร็จรูป** | สามารถเริ่มใช้งานได้รวดเร็ว มีฟังก์ชันพื้นฐานพร้อมใช้งาน และลดระยะเวลาในการพัฒนา                                                     | ฟังก์ชันอาจไม่ตรงกับกระบวนการแจ้งซ่อมของอาคารนอนทั้งหมด และอาจมีค่าใช้จ่ายด้าน License หรือการปรับแต่งระบบ   |
| **3. พัฒนาระบบเอง**           | สามารถออกแบบระบบให้ตรงกับความต้องการของผู้ใช้ ควบคุมรูปแบบการทำงานและข้อมูลได้ และเหมาะกับการเรียนรู้กระบวนการวิเคราะห์และออกแบบระบบ | ต้องใช้เวลาในการพัฒนา ทีมงานต้องมีความรู้ด้าน Web, Database และการทดสอบระบบ และต้องรับผิดชอบการบำรุงรักษาเอง |

### ทางเลือกที่แนะนำ

โครงการเลือก **การพัฒนาระบบเอง (In-house Development)** เนื่องจากทีมงานมีความรู้พื้นฐานด้านการวิเคราะห์ระบบ การพัฒนา Web Application การออกแบบส่วนติดต่อผู้ใช้ และฐานข้อมูล อีกทั้งระบบมีขอบเขตที่สามารถกำหนดให้เหมาะสมกับกระบวนการแจ้งซ่อมอาคารนอนได้โดยตรง

นอกจากนี้ การพัฒนาระบบเองช่วยให้สามารถปรับปรุงระบบในอนาคตตามความต้องการของหน่วยงานได้ โดยไม่จำเป็นต้องพึ่งพาซอฟต์แวร์สำเร็จรูปหรือผู้พัฒนาภายนอกทั้งหมด

## 1.3 Feasibility Assessment

การประเมินความเป็นไปได้ของโครงการพิจารณาในด้านเศรษฐกิจ ด้านเทคนิค และด้านการปฏิบัติงาน

### 1.3.1 Economic Feasibility

โครงการเป็นระบบที่พัฒนาขึ้นโดยทีมงานภายใน จึงสามารถลดค่าใช้จ่ายในการจัดซื้อซอฟต์แวร์สำเร็จรูปหรือการจ้างผู้พัฒนาภายนอกได้ ค่าใช้จ่ายหลักเกี่ยวข้องกับเครื่องคอมพิวเตอร์สำหรับพัฒนา ระบบฐานข้อมูล Hosting หรือ Server และทรัพยากรที่จำเป็นต่อการทดสอบระบบ

ประโยชน์ที่คาดว่าจะได้รับ ได้แก่ ลดเวลาในการประสานงาน ลดปัญหาข้อมูลตกหล่น และช่วยให้สามารถจัดเก็บข้อมูลการซ่อมและค่าใช้จ่ายอย่างเป็นระบบ ดังนั้นโครงการมีความเป็นไปได้ในด้านเศรษฐกิจ

### 1.3.2 Technical Feasibility

ทีมงานมีพื้นฐานด้านการพัฒนาซอฟต์แวร์ การวิเคราะห์และออกแบบระบบ การออกแบบ User Interface และการจัดการฐานข้อมูล สามารถนำเทคโนโลยี Web Application และ Database มาใช้ในการพัฒนาระบบได้

ระบบถูกออกแบบให้ผู้ใช้งานสามารถเข้าถึงผ่านอุปกรณ์ที่เชื่อมต่อเครือข่าย โดย Prototype ในระยะปัจจุบันออกแบบในรูปแบบ Mobile/iPhone เพื่อให้เหมาะกับการใช้งานของนักเรียนนายเรืออากาศ

ดังนั้นโครงการมีความเป็นไปได้ในด้านเทคนิค

### 1.3.3 Operational Feasibility

ระบบถูกออกแบบให้สอดคล้องกับกระบวนการทำงานจริง ตั้งแต่การแจ้งปัญหา การรับเรื่อง การมอบหมายงาน การซ่อม การบันทึกค่าใช้จ่าย และการปิดงาน

ผู้ใช้งานแต่ละกลุ่มจะได้รับสิทธิ์ตามบทบาทของตนเอง ทำให้สามารถใช้งานเฉพาะส่วนที่เกี่ยวข้องได้ และการออกแบบในรูปแบบ Mobile ช่วยให้ผู้ใช้งานสามารถแจ้งปัญหาได้สะดวกจากอุปกรณ์ที่ใช้งานอยู่

ดังนั้นโครงการมีความเป็นไปได้ในด้านการปฏิบัติงาน

## 1.4 Risk Management Plan

โครงการอาจพบความเสี่ยงระหว่างการพัฒนาและนำระบบไปใช้งาน จึงกำหนดความเสี่ยงและแนวทางรับมือดังนี้

| ความเสี่ยง                | ผลกระทบ                            | แนวทางป้องกัน/แก้ไข                                                    |
| ------------------------- | ---------------------------------- | ---------------------------------------------------------------------- |
| การพัฒนาไม่เสร็จตามกำหนด  | ส่งผลต่อกำหนดส่งโครงการ            | แบ่งงานเป็นระยะ กำหนดงานที่สำคัญก่อน และติดตามความคืบหน้าอย่างสม่ำเสมอ |
| สมาชิกมีเวลาไม่ตรงกัน     | งานบางส่วนล่าช้า                   | กำหนดหน้าที่ชัดเจนและใช้ช่องทางสื่อสารร่วมกัน                          |
| ปัญหาด้านเทคนิค           | ระบบบางส่วนไม่สามารถทำงานได้ตามแผน | ทดลองและทดสอบเป็นระยะ รวมถึงเลือกเทคโนโลยีที่ทีมมีความรู้              |
| ข้อมูลสูญหายหรือผิดพลาด   | ส่งผลต่อความน่าเชื่อถือของระบบ     | สำรองข้อมูลและตรวจสอบข้อมูลก่อนบันทึก                                  |
| ผู้ใช้ไม่เข้าใจวิธีใช้งาน | ระบบถูกใช้งานไม่เต็มประสิทธิภาพ    | ออกแบบ UI ให้เข้าใจง่าย และจัดทำคำแนะนำการใช้งาน                       |
| ระบบมีข้อผิดพลาดหลังพัฒนา | กระทบต่อการใช้งาน                  | จัดทำ Test Case และทดสอบระบบก่อนนำไปใช้งานจริง                         |

การจัดการความเสี่ยงจะดำเนินการควบคู่ไปกับการพัฒนา โดย Project Manager จะติดตามปัญหาและประเมินผลกระทบเพื่อกำหนดแนวทางแก้ไขที่เหมาะสม

## 1.5 Time and Schedule

การดำเนินโครงการแบ่งออกเป็น 6 ระยะหลัก ได้แก่ Planning, Analysis, Design, Development, Testing และ Deployment

| ระยะ                     | งานหลัก                                                 | ผลลัพธ์                                      |
| ------------------------ | ------------------------------------------------------- | -------------------------------------------- |
| **Phase 1: Planning**    | กำหนดปัญหา วัตถุประสงค์ ขอบเขต ทางเลือก และแผนโครงการ   | Project Plan                                 |
| **Phase 2: Analysis**    | วิเคราะห์ปัญหา ผู้ใช้งาน Requirements และกระบวนการทำงาน | Requirements, Context Diagram, DFD, Use Case |
| **Phase 3: Design**      | ออกแบบฐานข้อมูล UI และ Workflow                         | ER Diagram, Data Dictionary, UI Design       |
| **Phase 4: Development** | พัฒนาระบบตามแบบที่กำหนด                                 | ระบบต้นแบบ/ระบบที่พัฒนา                      |
| **Phase 5: Testing**     | ทดสอบฟังก์ชันและกระบวนการทำงานของระบบ                   | Test Cases และผลการทดสอบ                     |
| **Phase 6: Deployment**  | ติดตั้ง ทดลองใช้งาน และปรับปรุงระบบ                     | ระบบพร้อมใช้งาน                              |

การดำเนินงานจะมีการติดตามความคืบหน้าของแต่ละระยะอย่างต่อเนื่อง โดย Project Manager รับผิดชอบในการกำหนดลำดับงาน ติดตามปัญหา และประสานงานระหว่างสมาชิกในทีม

## 1.6 Team Configuration and Management

โครงการมีสมาชิกทั้งหมด 3 คน โดยแบ่งหน้าที่ตามความถนัดของสมาชิก และกำหนดให้สมาชิกสามารถช่วยเหลืองานส่วนอื่นของโครงการได้ตามความเหมาะสม

| สมาชิก                        | บทบาทหลัก                                  | หน้าที่รับผิดชอบ                                                                                                 |
| ----------------------------- | ------------------------------------------ | ---------------------------------------------------------------------------------------------------------------- |
| **นนอ.กฤตเมธ จันทสุด**        | Frontend / UI/UX                           | ออกแบบ User Interface, Figma, Canva/PowerPoint และ Interactive Prototype                                         |
| **นนอ.อภิรักษ์ สาจันทร์**     | Project Manager / System Analyst / Backend | วางแผนโครงการ วิเคราะห์ Requirements ออกแบบ Workflow เชื่อม Interactive Links จัดทำ Mockup Data และพัฒนา Backend |
| **นนอ.ธัญศิษฏ์ ศักดิ์ชัยศรี** | Database / Documentation                   | ออกแบบฐานข้อมูล Data Mapping จัดทำ Data Dictionary และจัดทำเอกสารโครงการ                                         |

กำหนด P (Primary) หมายถึงผู้รับผิดชอบหลัก และ S (Support) หมายถึงผู้สนับสนุนงาน

| งาน                             | กฤตเมธ | อภิรักษ์ | ธัญศิษฏิ์ |
| ------------------------------- | ------ | -------- | --------- |
| Requirements Analysis           | S      | **P**    | S         |
| Backend Development             | S      | **P**    | S         |
| UI/UX Design                    | **P**  | S        | -         |
| Database Design                 | -      | S        | **P**     |
| Test Scenario                   | S      | S        | **P**     |
| System Testing                  | S      | S        | **P**     |
| Documentation                   | S      | S        | **P**     |
| Project Feedback / Coordination | S      | **P**    | S         |

### การบริหารทีม

Project Manager ทำหน้าที่กำหนดแผนงาน ติดตามความคืบหน้า รวบรวมปัญหา และประสานงานระหว่างสมาชิก โดยสมาชิกทุกคนสามารถเสนอความคิดเห็นและช่วยเหลืองานของสมาชิกคนอื่นได้ เพื่อให้โครงการสามารถดำเนินงานได้ตามเป้าหมาย

ทีมจะมีการสื่อสารและติดตามความคืบหน้าของงานอย่างต่อเนื่อง รวมถึงตรวจสอบผลลัพธ์ของแต่ละ Phase ก่อนเริ่มดำเนินงานใน Phase ถัดไป
