# เอกสารอธิบายการทำงานของระบบ (Interactive Web Prototype)

**ระบบแจ้งซ่อมอาคารนอน** — นักเรียนนายเรืออากาศ

เอกสารนี้อธิบาย "ระบบทำงานอย่างไร" ตั้งแต่สถาปัตยกรรม ข้อมูล สถานะ ไปจนถึงวงจรการทำงานของแต่ละแจ้งซ่อมหนึ่งรายการ โดยอ้างอิงสถานะและคำเรียกตาม Prototype ปัจจุบันที่ใช้งานได้จริง

---

## 1. Architecture (สถาปัตยกรรมระบบ)

Prototype เป็น **Single Page Application (SPA)** เขียนด้วย HTML/CSS/JavaScript เหตุผลที่เลือกเป็น Web Application แทนการจำลองใน Figma เพราะต้องให้การทำงานจริง (เช่น กด "รับเรื่อง" แล้วสถานะเปลี่ยนจริง) ทำงานได้เหมือนระบบจริง ดูส่วน 4.2 ของ `step4-system-design.md`

โครงสร้างการทำงานเมื่อเปิดระบบ:

```
index.html  (หน้าแรกที่โหลดสไตล์ + ไฟล์ JS + ตัวหลัก)
    │
    ▼
Router (แปล URL hash → เลือกหน้าจอ + ตรวจสอบสิทธิ์)
    │
    ├──► หน้า Login หรือ App Shell (Sidebar + Topbar + Bottom Nav)
    │
    ▼
Pages (หน้าจอแต่ละหน้า: render เนื้อหา + bind การกดปุ่ม)
    │
    ▼
State Manager (SM)  — แหล่งข้อมูลกลางเดียวของทั้งระบบ
    │
    ▼
localStorage  (เก็บข้อมูลให้อยู่ข้ามการรีเฟรช)
```

**ไฟล์หลักและหน้าที่:**

| ไฟล์ | หน้าที่ |
| --- | --- |
| `index.html` | จุดเริ่มต้น โหลดไฟล์ทั้งหมดเข้าหน้าเดียว |
| `js/app.js` | Router + ตรวจสอบสิทธิ์ + โครงหน้าหลัก (Shell/Nav) + Logout |
| `js/state-manager.js` | State Manager (SM) — อ่าน/เขียนข้อมูลชุดเดียวกลางระบบ |
| `js/mock-data.js` | ข้อมูลเริ่มต้น (Seed) — บัญชีผู้ใช้, งานแจ้งซ่อม, รายการอ้างอิง |
| `js/components.js` | UI ชิ้นส่วนร่วม (การ์ดสรุป, แท็กสถานะ, ฟอร์ม ฯลฯ) |
| `js/pages/…` | หน้าจอแต่ละหน้า (ดูผนวก หัวข้อ 10) |

จุดสำคัญ: **ทุกหน้าจอไม่แยกข้อมูลกัน** — ทุกหน้าเรียกใช้งาน State Manager ชุดเดียวกัน ทำให้ช่างที่มอบหมายงานแล้วเห็นงานขึ้นในรายการของตนทันทีโดยไม่ต้องโหลดซ้ำหลายจุด

## 2. Authentication & RBAC (การเข้าสู่ระบบและสิทธิ์ตามบทบาท)

- ผู้ใช้กรอก **Username + Password** ระบบตรวจสอบกับบัญชีในฐานข้อมูลจำลอง `repair.users`
- ตรวจผ่าน → เก็บ **Session** ไว้ใน `repair.currentUser` (`ชื่อผู้ใช้, ชื่อ, บทบาท`) และส่งไปยังหน้าหลักของบทบาทนั้น
- **Role-Based Access Control (RBAC)**: ทุกหน้า (ยกเว้น Login) ระบุบทบาทที่เข้าได้ หากผู้ใช้เปิดหน้าที่ไม่ใช่บทบาทของตน ระบบแสดงหน้าข้อความ "คุณไม่มีสิทธิ์เข้าถึงหน้านี้"

## 3. Data Model / State Schema (ข้อมูลที่ระบบจัดเก็บ)

ข้อมูลทั้งหมดเก็บเป็นกลุ่ม (Store) ใน localStorage 4 ส่วน

| ชื่อข้อมูล | เก็บไว้เพื่ออะไร |
| --- | --- |
| `repair.requests` | รายการแจ้งซ่อมทุกงาน (หัวใจของระบบ) |
| `repair.users` | บัญชีผู้ใช้ทั้งหมด (เพิ่ม/แก้ไข/ลบได้) |
| `repair.settings` | ข้อมูลอ้างอิง: อาคาร, ชั้น, ประเภทปัญหา |
| `repair.currentUser` | ผู้ใช้ที่เข้าสู่ระบบในขณะนี้ (Session) |

### 3.1 งานแจ้งซ่อม 1 รายการ (`repair.requests`)

| ฟิลด์ | ความหมาย / ตัวอย่าง |
| --- | --- |
| `id` | เลขที่ใบแจ้งซ่อม เช่น `REP-0001` (สร้างอัตโนมัติเรียงลำดับ) |
| `ts` | เวลาจริงเป็นตัวเลข (ใช้จัดเรียง/คำนวณช่วงเวลา) |
| `reporter`, `reporterUser` | ชื่อผู้แจ้ง และ Username |
| `building`, `floor`, `room` | ตำแหน่งห้องที่แจ้ง (อาคาร/ชั้น/ห้อง) |
| `problemType`, `urgency` | ประเภทปัญหา (ไฟฟ้า/ประปา/แอร์/…) และความเร่งด่วน (ปกติ/ด่วน) |
| `description` | รายละเอียดปัญหาจากผู้แจ้ง |
| `photo` | รูปภาพประกอบ (หรือค่าว่าง) |
| `submittedAt` | วันที่/เวลาที่แจ้ง |
| `status` | สถานะปัจจุบัน (รอตรวจสอบ / รับเรื่อง / กำลังซ่อม / ซ่อมเสร็จ) |
| `assignedTechnician`, `assignedAt` | ช่างที่ได้รับมอบหมาย และเวลามอบหมาย |
| `startAt`, `completedAt` | เวลาเริ่มซ่อม และเวลาซ่อมเสร็จ |
| `repairResult` | ผลการซ่อม (ช่างกรอก) |
| `expense` | ค่าใช้จ่ายชุดเดียว: **อะไหล่ (รายการ/จำนวน/ราคาต่อหน่วย) + ค่าแรง + ค่าใช้จ่ายอื่น** |
| `history` | บันทึกเหตุการณ์ (Event log) ดูหัวข้อ 7 |

> ฟิลด์ `status`, `assignedTechnician`, `expense` และ `history` เป็นตัวทำให้ work flow เดินต่อกันได้ เช่น หน้า Tracking นำ `history` ไปแสดง Timeline และหน้า Report นำ `expense` ไปรวมยอดค่าใช้จ่าย

### 3.2 บัญชีผู้ใช้ (`repair.users`)

แต่ละบัญชีเก็บ `Username, รหัสผ่าน, ชื่อ, บทบาท (cadet/admin/tech/exec)` — เริ่มต้นมี 4 บัญชี (ตารางหัวข้อ 2) และเพิ่ม/แก้ไข/ลบได้จากหน้า "ผู้ใช้และสิทธิ์"

### 3.3 ข้อมูลอ้างอิง (`repair.settings`)

เก็บรายการ **อาคาร, ชั้น, ประเภทปัญหา** — ฟอร์มแจ้งซ่อมจะอ่านรายการเหล่านี้ไปสร้าง Dropdown และผู้ดูแลอาคารปรับได้จากหน้า "ผู้ใช้และสิทธิ์"

## 4. Status Workflow (สถานะและเงื่อนไขการเปลี่ยน)

**4 สถานะเท่านั้น** (ไม่มีสถานะ "ปฏิเสธ" หรือ "มอบหมายแล้ว"):

```
รอตรวจสอบ  ──รับเรื่อง──►  รับเรื่อง  ──เริ่มงาน──►  กำลังซ่อม  ──ปิดงาน──►  ซ่อมเสร็จ
```

| สถานะ | ความหมาย | ใครเปลี่ยน | เงื่อนไข |
| --- | --- | --- | --- |
| รอตรวจสอบ | ผู้แจ้งส่งคำขอมาแล้ว ยังไม่ตรวจ | ระบบ (ตอนแจ้งซ่อม) | — |
| รับเรื่อง | ผู้ดูแลตรวจสอบแล้วรับงานเข้า | ผู้ดูแลอาคาร | ต้องเป็นสถานะ "รอตรวจสอบ" |
| กำลังซ่อม | ช่างเริ่มลงมือซ่อมแล้ว | ช่าง | ต้องเป็น "รับเรื่อง" และมีช่างที่มอบหมายแล้ว |
| ซ่อมเสร็จ | จบงาน บันทึกผล + ค่าใช้จ่ายแล้ว | ช่าง | ต้องเป็น "กำลังซ่อม" และต้องกรอกผลการซ่อมก่อน |

ข้อสังเกต:
- **การมอบหมายช่างไม่เปลี่ยนสถานะ** — งานยังอยู่ใน "รับเรื่อง" จนกว่าช่างจะกดเริ่มงาน (แต่ช่างเห็นงานในรายการของตนทันทีที่ถูกมอบหมาย)
- **ปิดงานต้องมีผลการซ่อม** — ระบบไม่ให้ปิดงานโดยไม่มีผลการซ่อม

## 5. Role Workflow (การทำงานของแต่ละบทบาท)

| บทบาท | หน้าจอหลัก | ทำอะไรได้ |
| --- | --- | --- |
| **นักเรียนนายเรืออากาศ** | หน้าหลัก, แจ้งซ่อม, ติดตามสถานะ | แจ้งปัญหา (เลือกอาคาร/ชั้น/ห้อง/ประเภท + รายละเอียด/รูป), ดู Timeline สถานะของตัวเอง, ดูผลการซ่อมและค่าใช้จ่ายเมื่อเสร็จ |
| **ผู้ดูแลอาคาร** | รายการแจ้งซ่อม, ภาพรวม/รายงาน, ผู้ใช้และสิทธิ์ | ดูรายการทั้งหมด+กรอง/ค้นหา, **รับเรื่อง**, **มอบหมาย/เปลี่ยนช่าง**, ดูรายงานสรุปตามช่วงเวลา, เพิ่ม/ลบผู้ใช้, ตั้งค่าอาคาร/ชั้น/ประเภทปัญหา |
| **ช่าง** | งานของฉัน, รายละเอียดงาน | ดูงานที่มอบหมาย (แยกตามสถานะ), **เริ่มงาน** → กรอกผลการซ่อม + อะไหล่/ค่าแรง (ยอดรวมอัตโนมัติ) → **ปิดงาน** |
| **ผู้บังคับบัญชา** | ภาพรวม | ดูสถิติอย่างเดียว: งานตามสถานะ/ประเภท/อาคาร และค่าใช้จ่ายรวม |

## 6. Data Flow — ตัวอย่างงาน 1 รายการ (REP-0001)

ต่อไปนี้คือเส้นทางของงานแจ้งซ่อมหนึ่งรายการตั้งแต่ต้นจนจบ แสดงว่าแต่ละหน้าจออ่าน/เขียนข้อมูลชุดเดียวกัน (ผ่าน State Manager) จึงทำให้ข้อมูลเดินต่อกันได้

```
เริ่มต้นที่ "แจ้งซ่อม" (นักเรียน)
    │  เลือกอาคาร/ชั้น/ห้อง/ประเภท + รายละเอียด + รูป
    ▼
ระบบสร้างงาน REP-0001  (สถานะ = รอตรวจสอบ)
    │  เพิ่มเหตุการณ์แรก "สร้างคำขอแจ้งซ่อม" ลง history
    ▼
"รายการแจ้งซ่อม" (ผู้ดูแลอาคาร)  — เห็นงานในกลุ่ม "รอตรวจสอบ"
    │  เปิดรายละเอียด → กด "รับเรื่อง"
    ▼
สถานะ = รับเรื่อง  →  เลือกช่าง → กด "ยืนยันการมอบหมาย"
    │  กำหนด assignedTechnician = ช่างไฟฟ้า A
    │  (สถานะยังเป็น "รับเรื่อง" แต่ช่างเห็นงานทันที)
    ▼
"งานของฉัน" (ช่างไฟฟ้า A)  — งานปรากฏในรายการ
    │  เปิดงาน → กด "เริ่มงาน"
    ▼
สถานะ = กำลังซ่อม  →  กรอกผลการซ่อม + อะไหล่/ค่าแรง → กด "ปิดงาน"
    ▼
สถานะ = ซ่อมเสร็จ  (บันทึก completedAt)
    │
    ├──► "ติดตามสถานะ" (นักเรียน)
    │      └── แสดง Timeline ทุกขั้นตอน + ผลการซ่อม + ค่าใช้จ่ายรวม
    │
    └──► "ภาพรวม" (ผู้ดูแลอาคาร / ผู้บังคับบัญชา)
           └── งานนี้ถูกนับเข้าไปในสถิติและยอดค่าใช้จ่ายรวม
```

## 7. History & Timeline (ระบบรู้ได้อย่างไรว่า ขั้นตอนไหนเกิดเมื่อไร ใครทำ)

ทุกครั้งที่มีการกระทำ (Action) ระบบจะ **ต่อท้ายเหตุการณ์** ลงใน `history` ของงานนั้น โดยบันทึกสถานะหลังเหตุการณ์ เวลา ผู้กระทำ และรายละเอียด ซึ่งหน้า "ติดตามสถานะ" จะนำ array นี้ไปเรียงแสดงเป็น Timeline

ตัวอย่างเหตุการณ์ของงานที่ซ่อมเสร็จสมบูรณ์ (REP-0003):

| สถานะในเหตุการณ์ | เวลา | ผู้กระทำ | รายละเอียด |
| --- | --- | --- | --- |
| รอตรวจสอบ | 19 ก.ย. 2567 16:45 | นนอ.อาทิตย์ สว่าง | สร้างคำขอแจ้งซ่อม |
| รับเรื่อง | 19 ก.ย. 2567 17:00 | ร.อ.พิเชฐ ประจำอาคาร | ตรวจสอบและรับเรื่อง |
| รับเรื่อง | 19 ก.ย. 2567 17:00 | ร.อ.พิเชฐ ประจำอาคาร | มอบหมาย ช่างแอร์ C |
| กำลังซ่อม | 20 ก.ย. 2567 08:30 | ช่างแอร์ C | เริ่มดำเนินการซ่อม |
| ซ่อมเสร็จ | 20 ก.ย. 2567 11:00 | ช่างแอร์ C | บันทึกผลการซ่อมและปิดงาน |

ข้อควรเข้าใจ:
- `history` เก็บ **ทุกเหตุการณ์** ไม่ใช่เฉพาะตอนสถานะเปลี่ยน เช่น "มอบหมายช่าง" จึงมี 2 เหตุการณ์ "รับเรื่อง" ต่อกัน (เก็บบันทึกการรับเรื่อง และการมอบหมายช่าง)
- เหตุการณ์ที่เปลี่ยนช่างจะบันทึกเป็น "เปลี่ยนช่างจาก … เป็น …" เพื่อให้ตรวจสอบย้อนหลังได้

## 8. Persistence (การคงอยู่ของข้อมูล)

- ข้อมูลทั้งหมดเก็บใน **localStorage** ของเบราว์เซอร์ จึงอยู่ข้ามการรีเฟรช/ปิด-เปิดหน้าได้
- ครั้งแรกที่เปิดระบบจะ **Seed ข้อมูลตัวอย่าง** จาก `mock-data.js` (งานแจ้งซ่อม 9 รายการสถานะต่าง ๆ, 4 บัญชี, อาคาร/ชั้น/ประเภท) ครั้งถัดไปจะโหลดจากข้อมูลที่บันทึกไว้
- ระบบติดตามเวอร์ชันข้อมูล หากโครงสร้างเปลี่ยน (เวอร์ชันใหม่) จะสร้างชุดข้อมูลตัวอย่างขึ้นใหม่
- เหตุการณ์ storage ช่วยให้ข้อมูลอัปเดตข้ามแท็บได้ (เปิดหลายแท็บแล้วทำงานแท็บหนึ่ง อีกแท็บอัปเดตตาม)

## 9. Limitations (ข้อจำกัดของ Prototype)

| ทำได้ | ยังต้องใช้ระบบจริง (Backend/Database) |
| --- | --- |
| หน้าจอ + Flow + ตรรกะหลักครบทุกบทบาท | ฐานข้อมูลจริง ไม่ใช่ localStorage |
| ข้อมูลจำลองสถานะต่าง ๆ ครบ (9 งาน) | ข้อมูลข้ามเครื่อง/ผู้ใช้หลายคนพร้อมกัน |
| รับเรื่อง/มอบหมาย/เปลี่ยนช่าง/ปิดงาน เปลี่ยนสถานะจริง | สิทธิ์และการเข้ารหัสจริง (HTTPS, hashing) |
| ยอดค่าใช้จ่ายรวมอัตโนมัติ + รายงานตามช่วงเวลา | เก็บรูปภาพบนเซิร์ฟเวอร์ + Push Notification |
| อธิบายในส่วนวิเคราะห์/ออกแบบ (Use Case, ER, DFD) ได้จริง | Backup, Log, การเจาะจงสิทธิ์เชิงลึก, Deployment |

Prototype นี้เป็น **Interactive Web Prototype** ที่ทำให้ผู้ใช้/ผู้ประเมินทดสอบได้เหมือนใช้จริงตั้งแต่ Login ถึงรายงาน — ระบบจริงจะนำโครงสร้างเดียวกันไปติดตั้งบน Backend + Database ในขั้นตอนการพัฒนาถัดไป (ดู step2 / step5)
