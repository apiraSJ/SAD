# ส่วนที่ 2: การระบุปัญหาและข้อเสนอแนะ (Problem Identification & Recommendation)

---

## 2.1 Problem and Opportunity Statement

### คำชี้แจงปัญหา (Problem Statement)

ปัจจุบันกระบวนการแจ้งปัญหาความชำรุดเสียหายภายในอาคารนอนของนักเรียนนายเรืออากาศยังไม่มีระบบที่เป็นมาตรฐานเดียวกัน โดยการแจ้งปัญหาดำเนินการผ่านช่องทางที่หลากหลายและไม่เป็นระบบ ได้แก่ การแจ้งด้วยวาจา การแจ้งผ่าน LINE กลุ่ม หรือการบันทึกเป็นเอกสาร ซึ่งส่งผลให้เกิดปัญหาหลักดังนี้

**ปัญหาด้านการจัดการข้อมูล**
- ข้อมูลการแจ้งซ่อมกระจัดกระจายอยู่ในหลายช่องทาง ไม่สามารถรวบรวมเป็นฐานข้อมูลเดียวกันได้
- ข้อมูลบางส่วนอาจสูญหายหรือไม่ครบถ้วน เนื่องจากไม่มีรูปแบบการบันทึกที่ตายตัว
- ไม่สามารถดึงข้อมูลย้อนหลังเพื่อวิเคราะห์สถิติหรือแนวโน้มของปัญหาได้อย่างมีประสิทธิภาพ

**ปัญหาด้านการติดตามงาน**
- ผู้แจ้งไม่สามารถตรวจสอบสถานะของงานซ่อมได้ด้วยตนเอง ต้องสอบถามซ้ำแล้วซ้ำเล่า
- ผู้ดูแลอาคารไม่สามารถเห็นภาพรวมของงานที่ค้างอยู่ได้อย่างชัดเจน
- การมอบหมายงานไม่มีการบันทึกเป็นทางการ ทำให้ไม่ทราบว่าใครเป็นผู้รับผิดชอบงานไหน

**ปัญหาด้านความซ้ำซ้อน**
- ปัญหาเดียวกันอาจถูกแจ้งซ้ำโดยผู้อยู่อาศัยหลายคน โดยไม่ทราบว่ามีการแจ้งไปแล้ว
- เจ้าหน้าที่ต้องใช้เวลาตรวจสอบและคัดกรองปัญหาซ้ำซ้อนด้วยตนเอง

**ปัญหาด้านการบริหารจัดการ**
- ไม่มีการบันทึกค่าใช้จ่ายในการซ่อมแต่ละงานอย่างเป็นระบบ
- ไม่สามารถออกรายงานสรุปเพื่อประกอบการตัดสินใจบริหารจัดการอาคารนอนได้

### คำชี้แจงโอกาส (Opportunity Statement)

การพัฒนาระบบแจ้งซ่อมอาคารนอนจะช่วยแก้ปัญหาดังกล่าวและเปิดโอกาสในการพัฒนาองค์กรในหลายมิติ ได้แก่

1. **โอกาสในการเพิ่มประสิทธิภาพ** — การรวมศูนย์ข้อมูลการแจ้งซ่อมเข้าสู่ระบบเดียวช่วยลดเวลาในการประสานงานและติดตามงาน จากเดิมที่ต้องใช้การสื่อสารหลายช่องทาง
2. **โอกาสในการติดตามและตรวจสอบ** — ผู้ใช้งานทุกฝ่ายสามารถตรวจสอบสถานะงานได้แบบ Real-time ทำให้โปร่งใสและตรวจสอบได้
3. **โอกาสในการวิเคราะห์ข้อมูล** — ข้อมูลประวัติการซ่อมที่สะสมในระบบสามารถนำไปวิเคราะห์เพื่อวางแผนการบำรุงรักษาเชิง预防 (Preventive Maintenance) ได้
4. **โอกาสในการพัฒนาต่อยอด** — ระบบที่พัฒนาสามารถขยายไปใช้กับอาคารอื่นของหน่วยงาน หรือเชื่อมต่อกับระบบบริหารจัดการอาคารในอนาคตได้
5. **โอกาสในการเรียนรู้** — ทีมพัฒนาได้ฝึกฝนกระบวนการวิเคราะห์และออกแบบระบบตามหลักการ Systems Analysis and Design อย่างครบวงจร

## 2.2 Stakeholders

ผู้มีส่วนได้ส่วนเสียในระบบมีบทบาทหน้าที่และความต้องการที่แตกต่างกัน ดังนี้

| ผู้มีส่วนได้ส่วนเสีย | บทบาทในระบบ | ความต้องการ/ความคาดหวัง |
| --- | --- | --- |
| **นักเรียนนายเรืออากาศ / ผู้อยู่อาศัย** | ผู้แจ้งปัญหา (Requester) | สามารถแจ้งปัญหาได้ง่าย สะดวก รวดเร็ว และติดตามสถานะงานได้ด้วยตนเอง |
| **ผู้ดูแลอาคาร (Building Manager)** | ผู้ตรวจสอบและมอบหมายงาน (Dispatcher) | ได้รับข้อมูลครบถ้วน สามารถคัดกรองปัญหาซ้ำซ้อน และมอบหมายงานให้ช่างได้อย่างเหมาะสม |
| **ช่างซ่อม (Technician)** | ผู้ปฏิบัติงานซ่อม (Resolver) | ได้รับรายละเอียดงานที่ชัดเจน สามารถบันทึกผลการซ่อมและค่าใช้จ่ายได้สะดวก |
| **ผู้บังคับบัญชา / ฝ่ายธุรการ** | ผู้ตรวจสอบข้อมูล (Reporter) | สามารถดูภาพรวมรายงานสถิติการซ่อม ค่าใช้จ่าย และแนวโน้มปัญหาได้ |
| **ผู้ดูแลระบบ (Admin)** | ผู้จัดการข้อมูลและสิทธิ์ (Administrator) | จัดการข้อมูลผู้ใช้ สิทธิ์การใช้งาน และตั้งค่าระบบต่างๆ ได้สะดวก |
| **ฝ่ายอาคารสถานที่ (Facility Department)** | ผู้ดูแลอาคารนอนโดยรวม | ได้รับข้อมูลสรุปเพื่อวางแผนการบำรุงรักษาและจัดสรรงบประมาณ |

## 2.3 User Requirements

ความต้องการของผู้ใช้แต่ละกลุ่มถูกรวบรวมจากการวิเคราะห์กระบวนการทำงานจริงของอาคารนอน

### 2.3.1 ความต้องการของนักเรียนนายเรืออากาศ / ผู้อยู่อาศัย

| รหัส | ความต้องการ |
| --- | --- |
| UR-01 | สามารถแจ้งปัญหาได้โดยเลือกอาคาร ห้อง และประเภทปัญหาจากรายการ |
| UR-02 | สามารถกรอกรายละเอียดปัญหาและแนบรูปภาพประกอบได้ |
| UR-03 | สามารถตรวจสอบสถานะงานแจ้งซ่อมของตนเองได้ |
| UR-04 | สามารถดูประวัติการแจ้งซ่อมที่เคยทำไว้ย้อนหลังได้ |
| UR-05 | ได้รับการแจ้งเตือนเมื่อสถานะงานมีการเปลี่ยนแปลง |

### 2.3.2 ความต้องการของผู้ดูแลอาคาร

| รหัส | ความต้องการ |
| --- | --- |
| UR-06 | สามารถดูรายการแจ้งซ่อมที่เข้ามาใหม่ทั้งหมดได้ |
| UR-07 | สามารถตรวจสอบและคัดกรองปัญหาซ้ำซ้อนก่อนรับเรื่องได้ |
| UR-08 | สามารถมอบหมายงานให้ช่างซ่อมแต่ละคนได้ |
| UR-09 | สามารถติดตามสถานะงานทั้งหมดที่อยู่ในความรับผิดชอบได้ |
| UR-10 | สามารถดูรายงานสรุปงานซ่อมตามช่วงเวลาได้ |

### 2.3.3 ความต้องการของช่างซ่อม

| รหัส | ความต้องการ |
| --- | --- |

| UR-12 | สามารถบันทึกผลการซ่อมและสถานะงานได้ |
| UR-13 | สามารถบันทึกค่าใช้จ่ายวัสดุอุปกรณ์ในการซ่อมได้ |

### 2.3.4 ความต้องการของผู้บังคับบัญชา / ฝ่ายธุรการ

| --- | --- |

| UR-15 | สามารถดูข้อมูลค่าใช้จ่ายรวมของการซ่อมแซมได้ |

## 2.4 System Requirements

ความต้องการของระบบในเชิงเทคนิคเพื่อให้สามารถรองรับความต้องการของผู้ใช้ได้อย่างมีประสิทธิภาพ

### 2.4.1 Hardware Requirements

| รายการ | ความต้องการ |
| --- | --- |
| **Server** | เครื่องคอมพิวเตอร์สำหรับเป็น Server ประสิทธิภาพปานกลาง รองรับ Web Application และ Database |
| **Client (ผู้ใช้ทั่วไป)** | สมาร์ทโฟน แท็บเล็ต หรือคอมพิวเตอร์ที่เชื่อมต่ออินเทอร์เน็ตได้ |
| **Storage** | พื้นที่จัดเก็บข้อมูลสำหรับฐานข้อมูลและรูปภาพประกอบ (ไม่น้อยกว่า 10 GB) |

### 2.4.2 Software Requirements

| รายการ | ความต้องการ |
| --- | --- |
| **Operating System (Server)** | Linux (Ubuntu/CentOS) หรือ Windows Server |
| **Web Server** | Apache หรือ Nginx |
| **Backend Language** | PHP / Node.js / Python (หรือเทคโนโลยีที่ทีมเลือก) |
| **Database Management System** | MySQL / PostgreSQL |
| **Frontend** | HTML5, CSS3, JavaScript (หรือ Framework ที่เหมาะสม เช่น React, Vue) |
| **Browser** | รองรับ Chrome, Safari, Edge บนอุปกรณ์เคลื่อนที่และเดสก์ท็อป |

### 2.4.3 Network Requirements

| รายการ | ความต้องการ |
| --- | --- |
| **การเชื่อมต่อ** | ระบบต้องสามารถเข้าถึงผ่านเครือข่ายอินเทอร์เน็ตหรือเครือข่ายภายในของหน่วยงาน |
| **ความเร็ว** | รองรับการใช้งานพร้อมกันหลาย User โดยไม่มีปัญหาด้านประสิทธิภาพ |
| **Protocol** | HTTPS สำหรับการสื่อสารที่ปลอดภัย |

### 2.4.4 Security Requirements

| รหัส | ความต้องการ |
| --- | --- |
| SEC-01 | ระบบต้องมีการเข้าสู่ระบบ (Login) ด้วยชื่อผู้ใช้และรหัสผ่าน |
| SEC-02 | ระบบต้องมีการกำหนดสิทธิ์การใช้งานตามบทบาท (Role-Based Access Control) |
| SEC-03 | ข้อมูลที่ส่งผ่านระบบต้องเข้ารหัสด้วย HTTPS |
| SEC-04 | ข้อมูลรหัสผ่านต้องถูกเข้ารหัส (Hashing) ก่อนจัดเก็บในฐานข้อมูล |
| SEC-05 | ระบบต้องมีการบันทึก Log การเข้าใช้งานและการทำรายการสำคัญ |

### 2.4.5 Performance Requirements

| รายการ | ความต้องการ |
| --- | --- |
| **เวลาตอบสนอง** | หน้าจอต้องโหลดและแสดงผลภายใน 3 วินาที |
| **การรองรับผู้ใช้** | ระบบต้องรองรับผู้ใช้งานพร้อมกันได้อย่างน้อย 50 User |
| **Availability** | ระบบต้องพร้อมใช้งานไม่น้อยกว่า 95% ของเวลาทั้งหมด |
| **Data Backup** | ข้อมูลต้องมีการสำรองข้อมูลอย่างสม่ำเสมอ (Daily Backup) |
